# CrowdStrike Detection Rules — Simulated Multi-Technique Attack Chain

Detection rule documentation and deployable query logic for four MITRE ATT&CK techniques, derived from a threat hunt against Atomic Red Team test execution captured via CrowdStrike Falcon telemetry.

## About

This repository documents four detection rules deployed to CrowdStrike, covering a single simulated attack chain observed on one host and user account. Each rule is provided in two formats:

- **Markdown (`.md`)** — human-readable documentation for analysts, covering the rule's goal, MITRE mapping, detection logic, known blind spots, expected false positives, priority/severity breakdown, validation steps, and recommended incident response actions.
- **YAML (`.yaml`)** — structured, machine-parseable version of the same content, suitable for version control, automated rule management, or ingestion into other tooling.

Both formats contain the identical CrowdStrike LogScale (CQL) query logic, fully commented line-by-line.

**Techniques covered:**

| # | Technique | MITRE ID | Tactic | Severity |
|---|---|---|---|---|
| 001 | Masquerading — Double File Extension | [T1036.007](https://attack.mitre.org/techniques/T1036/007/) | Defense Evasion | High |
| 002 | Command and Scripting Interpreter | [T1059.001](https://attack.mitre.org/techniques/T1059/001/), [T1059.003](https://attack.mitre.org/techniques/T1059/003/) | Execution | Critical / High |
| 003 | Scheduled Task/Job (incl. registry-based "Ghost Task") | [T1053.005](https://attack.mitre.org/techniques/T1053/005/) | Execution, Persistence, Privilege Escalation | Critical / High / Medium |
| 004 | Account Discovery | [T1087.001](https://attack.mitre.org/techniques/T1087/001/), [T1087.002](https://attack.mitre.org/techniques/T1087/002/) | Discovery | Medium |

Each numbered pair (`.md` + `.yaml`) documents one deployed rule and shares the same structure:

- **Goal** — what the rule is designed to catch
- **Categorization** — MITRE ATT&CK tactic/technique/sub-technique mapping
- **Strategy Abstract** — how the detection logic works, at a glance
- **Technical Context** — why the underlying behavior matters and how it's typically exploited
- **Query** — the full, commented CrowdStrike LogScale (CQL) logic
- **Blind Spots and Assumptions** — known gaps and telemetry dependencies
- **False Positives** — expected sources of benign noise and how they're handled
- **Priority** — how `_Risk` output values map to severity
- **Validation** — which Atomic Red Team test(s) the rule was validated against
- **Response** — recommended triage/investigation steps if the rule fires

## Tooling & Platform

- **Log source:** CrowdStrike Falcon (process, file, scheduled-task, and registry telemetry)
- **Query language:** CrowdStrike LogScale (CQL)
- **Test framework:** [Atomic Red Team](https://github.com/redcanaryco/atomic-red-team) (Red Canary)
- **Reference:** [MITRE ATT&CK](https://attack.mitre.org/)

## Deployment Status

All four rules are deployed as live detection rules in CrowdStrike. Rule 002 (Command and Scripting Interpreter) has a documented scope limitation — several of its match conditions are tuned to specific artifacts from the source investigation (filenames, staging domains) rather than fully generalized behavior, and a broader version is noted as a recommended follow-up in its documentation.

## Intended Use

The YAML files are the structured source of truth for each rule's metadata and query logic; the Markdown files are the same information formatted for readability during analyst review, onboarding, or documentation handoff. When updating a rule, keep both formats in sync.

## Disclaimer

All activity referenced in this repository was generated by authorized Atomic Red Team test execution in a controlled environment, not a real-world intrusion. Detection thresholds, allow-lists, and severity mappings documented here are starting points validated against one test environment and should be re-validated against your own environment's baseline before relying on them in production.
